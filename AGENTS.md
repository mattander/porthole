# Working preferences

- Never use type casts, type assertions, or explicit or implicit `any`. Validate external data at boundaries and model valid states with types.
- Prefer the simplest maintainable design that meets the requested scope. Preserve unrelated changes and avoid unrelated cleanup.
- Read relevant project documentation. Keep durable conventions here and detailed procedures, plans and progress in linked documents.
- Use agent teams or councils only when requested. Preserve the selected model unless the user asks to change it.
- Ask only when missing information materially changes the outcome or required authority is absent. Reuse decisions and approvals already given; continue independent work while awaiting an answer.
- Run relevant checks and reuse valid final-state evidence. Report results and material gaps concisely; distinguish observed results from assumptions.

# Complete repository tasks

- When asked to make a change in a repository, the task is not complete until its pull request is merged and the change is in `main`.
- Carry the task through implementation, relevant verification, committing, pushing, opening a pull request and merging it. Do not stop at a local edit, passing checks, a pushed branch or an open pull request.
- Follow repository review, check and merge requirements. Do not bypass required reviews, failing checks or branch protections to finish a task.
- Continue through the authorized workflow without another discretionary permission question. Honor explicit local-only, no-push, draft-only or other scope limits; required tool approvals and authority checks still apply.
- Verify the pull request's merged status and that `main` contains the resulting change before reporting completion. Sync the local checkout to `main` when doing so preserves unrelated work.
- If a concrete blocker prevents completion, finish independent authorized work and report the blocker and remaining step clearly. Do not describe unfinished work as complete.
